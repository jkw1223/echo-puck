# Steve / Puck 0

A first-generation Echo Show 5 (`checkers`) running LineageOS Android 11 serves as a thin audio/display endpoint. The current prototype sends a recorded turn over Wi-Fi to a Mac relay and receives a fixed spoken test reply and caption. It does not yet connect to ChatGPT or a model.

Read [CURRENT_STATE.md](CURRENT_STATE.md) for the live acceptance evidence and exact resume point. Older September 5 bring-up notes are not the current state.

## Components

- `puckd-android`: Android Activity, foreground connection service, and media turn controller.
- `puck-relay`: Node control and media relay; test voice fixtures.
- `puckd-files`: Original loose scaffolding; retained as reference, not the build source.
- `artifacts`: Timestamped build/test/device evidence and previous application backups.

## Build and run

Relay:

```sh
cd /Users/jason/puck/puck-relay
npm install
npm test
npm start
```

Before starting, check `lsof -nP -iTCP:8787 -sTCP:LISTEN` for an existing relay. It listens on `0.0.0.0:8787` (`PORT` overrides it). `/health` reports control connection state. The macOS host application launching Node needs Local Network access; Jason approved its prompt during bring-up.

Android:

```sh
cd /Users/jason/puck/puckd-android
./gradlew :app:assembleDebug -PrelayUrl=ws://192.168.1.193:8787/puck
/Users/jason/Library/Android/sdk/platform-tools/adb -s 192.168.1.24:5555 install -r app/build/outputs/apk/debug/app-debug.apk
/Users/jason/Library/Android/sdk/platform-tools/adb -s 192.168.1.24:5555 shell am start -n com.steve.puckd/.MainActivity
```

Keep the same debug signing key for updates. The default relay is the Mac's current `.193` address; DHCP reservation/discovery is not implemented. The Activity starts the private service, so direct shell `start-foreground-service` is no longer the launch path. BootReceiver exists, but cold-boot recovery has not been tested. Network ADB persistence across reboot is not assumed.

## Device controls

- **Talk:** record microphone audio. Permission is requested when needed.
- **Finish:** stop capture and send the recording to the Mac. Maximum capture is 30 seconds, after which the turn is sent automatically.
- **Stop:** discard the current recording or stop a network/playback operation. Leaving the Activity also cancels it.
- **Test speaker:** play a short local tone without the relay.

The media path is half-duplex: record, upload, receive reply, play. No continuous listening or wake word. Speech stays in memory during this slice; the Mac logs byte counts/checksums, not raw recordings. The fixed reply is generated locally using macOS `say`, stored as 16 kHz mono PCM16, and explicitly labeled as a bridge test.

The earlier five-second local recording/replay implementation is retained in `LocalAudio.kt` and in the pre-media APK backup; the current screen focuses on the network turn.

## Control protocol

`/puck` uses WebSocket JSON protocol 1. Device heartbeats include increasing `id`, per-service UUID `session`, `deviceId` (Android ID), and device/model/Android strings. Relay acknowledgments echo `id` and `session`. Device RTT uses a monotonic clock. Next heartbeat is 15 seconds after acknowledgment; missing ACK after 8 seconds triggers reconnect with 2/4/8/16/30-second retry delays. The server expires heartbeat leases after 45 seconds, swept every 5 seconds.

`hello` now carries a random `mediaToken`. The Android service publishes it only while Connected in private app preferences, and clears it on disconnect. It is never logged. The server requires the corresponding WebSocket to still be OPEN and identified by a heartbeat. This ticket binds media to the current connection; it does not establish a trusted device identity.

## Media protocol

Separate HTTP requests keep recordings off the control WebSocket queue. All media requests carry `Authorization: Bearer <mediaToken>` and `X-Puck-Session: <session>`.

- `POST /turns/<UUID>`: `Content-Type: application/octet-stream`, `X-Puck-Format: pcm_s16le_16000_mono`. Body is little-endian PCM16, 16 kHz mono, 0.1–30 seconds (3,200–960,000 bytes). A declared content length is required and validated. Reply 202 echoes turn ID, received byte count, SHA-256.
- `GET /turns/<UUID>/reply`: one-time JSON response containing turn ID, `source: local_fixture`, caption, format, and base64 PCM. The Show validates identity/format/size and its live connection before playback.
- `DELETE /turns/<UUID>`: cancels pending upload/reply and remembers the turn ID so a delayed upload cannot resurrect it.

One active turn per connection. Turn state expires after 60 seconds; incomplete uploads time out after 15 seconds. Each connection remembers up to 512 turn IDs, then requires reconnection for more turns. Reply retrieval consumes the reply once; a lost response fails rather than replaying later. Uploads are never automatically retried.

Current transport is plaintext on the LAN. Persistent enrollment/authentication and TLS remain future work. Provider credentials, browser sessions, and model calls are not part of this slice.
